# CopySelect metadata clipboard hotfix audit — 2026-09-08

## Reproduced diagnosis

The reported Win+V entry proves the metadata block is present in the Windows clipboard itself. It is generated by CopySelect's `includeMetadata` formatting path, not by ChatGPT or the paste destination.

The first 3.7.8.17 repair changed the live `includeMetadata` flag but could leave `profiles.Default.includeMetadata=true`. Re-applying the Default profile could therefore restore the unwanted metadata.

## Fixes

1. Schema 29 migration repairs both the live affected Default/Rich Text/{text} state and the saved Default-profile snapshot.
2. Research and non-{text} custom metadata setups are preserved.
3. Ctrl+Shift+V is intercepted at the `paste` event, rather than relying only on the V keydown. This matters for browser-reserved shortcuts and complex editors.
4. Editable-target detection includes nested contenteditable and role=textbox hosts.
5. A local envelope is stored after every successful automatic CopySelect copy.
6. Background/session envelope resolution remains available across tabs/service-worker restarts.
7. Clipboard comparison normalizes CRLF/CR, NUL termination, NFC, and trailing newlines.

## Expected behavior after extension reload/reconnection

A normal CopySelect auto-copy in the affected Default/Rich Text setup writes the selected text as text/plain rather than title/domain/date/time/count/URL metadata. Ctrl+Shift+V uses the original raw selection when the current clipboard is the exact recent CopySelect-formatted payload.
